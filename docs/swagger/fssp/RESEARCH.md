# Исследование API-ФССП DaMIA

## Источники и границы

Основной источник — [страница API-ФССП](https://damia.ru/apifssp), полный снимок `/tmp/damia-fssp.txt` (727 строк); также прочитан предоставленный предыдущий отчёт разведки. Сервис принадлежит DaMIA; это не утверждение о прямом API ФССП. [Каталог](https://damia.ru/damapi) и [страница примеров](https://damia.ru/apicalls?id=1) заданы для контекста, но не использованы как подтверждение новых контрактов. Данные снимка и предыдущего отчёта совпадают. Платные и реальные API-запросы не выполнялись; ключи и реальные персональные данные в артефакты не включались.

## Исходный инвентарь и покрытие

Инвентарь страницы (строки 32–44, повторение в тарифном калькуляторе 685–707) содержит ровно четыре метода. Все используют GET и базу `https://api.damia.ru/fssp`.

| Метод | Путь | Назначение | Параметры запроса помимо key | Покрытие |
|---|---|---|---|---|
| isp | `/isp` | Производство ЮЛ по индивидуальному или сводному номеру, история | regn: string | GET, параметры, справочный перечень полей |
| isps | `/isps` | Действующие и завершённые производства ЮЛ | inn, from_date, to_date: string; format, page: integer | GET, оба формата, пагинация |
| ispfl | `/ispfl` | Производство ФЛ или ИП по номеру | regn: string | GET, параметры, справочный перечень полей |
| ispsfl | `/ispsfl` | Производства ФЛ | region, format, page: integer; fam, nam, otch, bdate: string | GET, оба формата, пагинация |

`from_date` и `to_date` задаются в формате YYYY-MM-DD; включительность границ неизвестна. `bdate` — DD.MM.YYYY. У `ispsfl` явно необязательны `region`, `otch`, `bdate`; `region` — код региона отдела судебных приставов, ведущего производство, а его отсутствие означает все регионы. Вводный текст упоминает дату рождения, но таблица называет её необязательной. В таблице примеры `fam` и `otch` ошибочно подписаны `nam=`, полные примеры используют корректные имена.

`format=1` означает группировку, `format=2` — без группировки, по умолчанию 2. `page` по умолчанию 1; максимум 100 производств на странице `isps` и 20 на странице `ispsfl`, а не максимальный номер страницы. Поведение страниц при группировке и метаданные пагинации не описаны. Значения по умолчанию позволяют предположить пропуск `format` и `page`, но реальное поведение не проверено. Обязательность остальных параметров явно не установлена; `required: false` в OpenAPI — компромисс представления, а не гарантия успешного запроса без них. Номера и ИНН остаются строками, чтобы не терять нули.

## Побочные эффекты

Документация описывает четыре GET как получение сведений, а не изменение производств. Тарифная секция указывает тарификацию по запросам для методов ФЛ; для методов ЮЛ калькулятор также предлагает тарификацию по номерам дел или организациям. Вызов может расходовать тарифную квоту или иметь стоимость; точные условия зависят от тарифа. Иные побочные эффекты источником не установлены.

## Авторизация и HTTP

Каждый метод перечисляет строковый query-параметр `key` как ключ доступа к API. Он представлен security scheme `apiKey` в query; его обязательность формально не оговорена, поэтому в `security` есть пустая альтернатива. Она не доказывает возможность анонимного доступа. Неизвестно, общий ли этот ключ с другими сервисами DaMIA; bearer/header-схемы не документированы. Не выводить ключ в логи и URL-диагностику.

Источник называет ответы JSON, однако точный HTTP Content-Type, коды успеха и ошибок, тела ошибок и семантика ошибок авторизации не указаны. Для машинного описания успешного ответа в OpenAPI использованы диапазон `2XX`, `application/json` и необременённая ограничениями схема: это представление описанного JSON, а не подтверждение конкретного статуса или HTTP-заголовка. `default` не утверждает конкретный статус, тип содержимого или JSON для ошибок. Шесть блоков ответов в снимке пусты; это не доказывает, что на живой странице нет раскрываемых примеров. Точные корень, вложенность, динамические ключи, типы элементов массивов, обязательность, nullable, пустой результат и числовое представление не проверены. Схемы компонентов — отдельные справочные перечни, не привязанные как схема реального ответа; `additionalProperties` допускает неизвестные ключи и не навязывает недоказанную форму. Расширение операций `x-documented-response-fields` содержит локальные ссылки на эти перечни для машинного поиска; оно не является стандартной схемой тела ответа и не устанавливает ни его структуру, ни HTTP-статус или медиа-тип. `ТипПост` встречается в остатках комментариев и не считается подтверждённым полем.

### Особенности ответа

* `isp`: `РегНомер` указан как array с неизвестными элементами. `Должник` содержит реквизиты ЮЛ, `Сумма` — общая задолженность, `Остаток` — оставшаяся. `История` описана объектом; `Дата` названа объектом и одновременно датой YYYY-MM-DD, `Поле` — предыдущим значением произвольного поля. Ключи и вложенность неизвестны.
* `isps`: при группировке `ИНН`, `Год`, `Статус`, `Предмет` указаны объектами, `Сумма` — float, `Количество` — integer, `ИП` — array без типа элементов. Их фактическая иерархия не подтверждена. Без группировки `ИНН` и `РегНомер` — объекты, приведены реквизиты производства и должника, суммы — double.
* `ispfl`: `result` и `РегНомер` — объекты, есть данные должника, пристава и исполнительского сбора. Здесь `Сумма` — **непогашенная**, а не общая задолженность. Запрос `regn` описан как индивидуальный номер, но описание `РегНомерСД` упоминает сводный номер в запросе; поддержка последнего не подтверждена.
* `ispsfl`: при format=1 перечислены `result`, `Год` и ссылка на поля объекта `Год` из `isps`; при format=2 — `result`, `РегНомер` и ссылка на поля объекта `РегНомер` из `ispfl`. Граница повторного использования и наличие динамических ключей неизвестны; корпоративная обёртка `ИНН` не предполагается.

## Приоритеты SDK и проверка

1. Получить у поставщика обезличенные примеры успешных ответов для всех четырёх методов и обоих форматов списков, включая несколько страниц и пустые результаты; установить реальные корни, динамические ключи, вложенность и типы массивов до генерации строгих моделей.
2. Уточнить обязательность каждого входа и ключа, совместимость ключей сервисов, коды/типы ошибок, точный Content-Type, лимиты, признак следующей страницы и границы дат.
3. Уточнить неоднозначность `ispfl` по номеру, `История.Дата` и границу ссылок `ispsfl`; подтвердить действительность поля `ТипПост` до включения.
4. В SDK сохранять идентификаторы строками, разные значения `Сумма`, локальную дату рождения без преобразования к ISO и не ограничивать статус закрытым enum. Не логировать секреты и персональные данные.
5. До появления фикстур использовать только синтетические данные; проверять OpenAPI 3.0.3, имена параметров, security, источники, ссылки, четыре GET и отсутствие дубликатов operationId. Результаты проверок приведены в отчёте выполнения.

Остаточный риск: даже корректный OpenAPI не подтверждает фактическое поведение API; строгая схема или генерация клиента по справочным перечням может ошибочно зафиксировать структуру ответа.
