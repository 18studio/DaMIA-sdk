# DaMIA API: исследовательские OpenAPI-спецификации

Этот каталог содержит самостоятельные спецификации OpenAPI 3.0.3, подготовленные по публичной документации DaMIA и связанных сервисов для проектирования SDK. Спецификации не являются официальными документами поставщика и не подтверждены вызовами API.

**Исследовательский статус:** спецификации всех восьми модулей созданы. Замечания ревью по `multcheck` ФНС, неподтверждённому POST-транспорту Банков и вариантам отчёта СПК исправлены и повторно проверены независимым ревьюером. Фактическое поведение API не проверено, поэтому не считайте файлы окончательным контрактом для генерации SDK.

## Инвентарь контрактов

[Матрица 61 операции и вопросы поставщику](../contracts/inventory.md) и [машиночитаемый снимок](../contracts/inventory.yaml) различают свидетельства `spec` (исследовательский OpenAPI), `research` (исследование источников), `sdk` (текущая реализация), `synthetic-test` (локальный mock) и `unknown` (неизвестное поведение сервера). Ни один уровень не подтверждает фактический серверный контракт; `2XX`, `required: false` и media types могут быть соглашениями моделирования.

## Swagger UI

Из корня проекта запустите статический HTTP-сервер:

```bash
python3 -m http.server 8000 --directory docs/swagger
```

Откройте <http://localhost:8000/> и выберите сервис в верхнем меню. Методы отображаются сразу; нажмите на нужный метод, чтобы раскрыть параметры и ответы. Если вы уже открывали прежнюю версию страницы, выполните принудительное обновление браузера. Открытие `index.html` напрямую через `file://` может не работать из-за ограничений браузера. Интерфейс загружает Swagger UI с CDN, поэтому требуется подключение к интернету.

Кнопка **Try it out** отправляет реальные запросы к DaMIA: они могут быть платными или изменять состояние, даже если метод использует GET. Возможность вызова из браузера также зависит от настроек CORS на стороне API. Авторизация не сохраняется при обновлении страницы; внешний онлайн-валидатор Swagger отключён.

## Mock-сервер Prism

Для запуска нужен Node.js с `npx`; при первом запуске пакет Prism скачивается из npm. Из корня проекта:

```bash
make prism                    # ФНС: http://127.0.0.1:4010
make prism-rosstat PORT=4011  # Росстат на другом порту
make prism SERVICE=scoring    # выбор сервиса через переменную
```

Доступные сервисы: `fns`, `rosstat`, `banks`, `scoring`, `procurement`, `arbitration`, `fssp`, `spk`. Один процесс обслуживает одну спецификацию; для одновременной работы запустите несколько команд в отдельных терминалах с разными портами. Остановить сервер можно через Ctrl+C.

Дополнительные параметры: `HOST` (по умолчанию `127.0.0.1`), `PORT` (по умолчанию `4010`), `DYNAMIC=1` для динамической генерации ответов, `PRISM_VERSION` и `PRISM_FLAGS` для дополнительных аргументов Prism. По умолчанию используется Prism 5.5.0. Команда `make help` показывает краткую справку. Не открывайте сервер на внешнем интерфейсе без необходимости.

Пример запроса к локальному mock ФНС:

```bash
curl -G http://127.0.0.1:4010/egr \
  --data-urlencode 'req=0000000000' \
  --data-urlencode 'key=test-key'
```

Prism сопоставляет маршруты с `paths` в спецификации: путь из `servers.url` в локальный адрес не добавляется. Поэтому у ФНС используется `/egr`, тогда как для арбитражей в сам путь включён префикс `/arb`, например `/arb/dela`.

Mock генерирует ответы по исследовательской спецификации, а не обращается к DaMIA. Пустые или неполные схемы не обеспечивают реалистичные ответы, и соответствие mock не подтверждает совместимость с реальным API. Для воспроизводимых SDK-тестов понадобятся отдельные синтетические фикстуры и сценарии ошибок.

## Публикация на GitHub Pages

Workflow [swagger-pages.yml](../../.github/workflows/swagger-pages.yml) публикует Swagger UI и файлы `*/openapi.yaml` при каждом push в ветку по умолчанию. Исследовательские отчёты и другие файлы репозитория в артефакт сайта не включаются. Его также можно запустить вручную из вкладки **Actions**.

Чтобы включить публикацию:

1. Создайте репозиторий на GitHub и отправьте туда проект с workflow и каталогом `docs/swagger`.
2. В репозитории откройте **Settings → Pages → Build and deployment** и выберите **GitHub Actions** как источник.
3. При необходимости запустите **Actions → Publish Swagger UI → Run workflow**. После успешного развёртывания URL появится в **Settings → Pages** и в результатах workflow. Для обычного репозитория он обычно имеет вид `https://<владелец>.github.io/<репозиторий>/`.

GitHub Pages может быть доступен публично даже при закрытом исходном репозитории — проверьте настройки и права доступа до публикации. Не включайте ключи или персональные данные в файлы сайта. Доступность Pages для приватных репозиториев зависит от тарифа GitHub.

## Как читать спецификации

- Это **исследовательская основа**, а не гарантированно полный wire-контракт. `RESEARCH.md` каждого сервиса фиксирует охват, источники, расхождения и неустановленные детали.
- API использует ключ `key`; документация не подтверждает, что один ключ или тариф действует на всех трёх доменах. Не записывайте ключи, URL с ключами и персональные данные в журналы.
- Для документированного JSON успешный ответ может быть обозначен группой `2XX`: это обобщение для OpenAPI, а не установленный конкретный HTTP-статус. Заголовки, ошибки и отдельные структуры нужно проверить на реальном API.
- Идентификаторы и данные финансовых показателей нельзя бездумно преобразовывать в числа: возможны ведущие нули и числовые значения в строках.
- Не все GET-запросы являются чтением: например, мониторинг и подписки могут изменять состояние. Не применяйте без разбора retry и кэширование.
- Генерация клиента из этих файлов даст стартовую заготовку, но не заменяет проверки всех схем, сериализации параметров, файлов и ошибок на тестовом доступе и конкретных тарифах.

## Валидация OpenAPI

Например, в отдельном виртуальном окружении Python:

```bash
python3 -m venv .venv-openapi
.venv-openapi/bin/pip install openapi-spec-validator==0.9.0
for file in docs/swagger/*/openapi.yaml; do
  .venv-openapi/bin/python -m openapi_spec_validator "$file"
done
```

Валидация проверяет соответствие структуре OpenAPI, но не подтверждает совпадение с фактическим поведением API, полноту описаний или доступность по тарифу. Для финализации нужны контрольные вызовы с разрешённым тестовым ключом, фиксация обезличенных примеров ответов и сверка неясных условий с поставщиком.
