## Авторизация и общая семантика HTTP

Обе таблицы называют `key` query-параметром с ключом доступа к API. Обязательность явно не указана, как и факт применимости одного и того же выданного ключа к обоим методам. В OpenAPI определены альтернативы `{}` OR query apiKey: формально они разрешают анонимный вызов, а не выражают неизвестную обязательность. Поэтому Swagger UI и генераторы могут не запросить ключ; это не обещание работоспособности вызова без него. Требование ключа в будущем контракте было бы политикой клиента, а не установленным требованием поставщика. Ключи не приводятся. Query-ключ может попадать в логи и историю URL: SDK должен маскировать его в логах и URL.

Оба метода используют HTTPS GET; побочные эффекты и стоимость отдельных вызовов по этим снимкам не установлены. При этом [тарифы СПК](https://damia.ru/apispk) и [тарифы проверок](https://damia.ru/apiproverki) предусматривают бесплатную квоту и платные планы: вызовы могут расходовать квоту или быть платными в зависимости от договора. Точная стоимость, списания и тарификация повторов не установлены. HTTP-коды успеха и ошибок, тела ошибок, точные Content-Type и обязательность полей не описаны. Успешные ответы представлены диапазоном `2XX` как соглашением моделирования, а не установленным источником диапазоном; `default` описывает прочие ответы без предположений о теле ошибок. Точный тип содержимого не угадан: в `content` используется общий media range `*/*`, а не утверждение о конкретном Content-Type. Схемы успешных ответов не ограничены: они не обеспечивают автоматический выбор типизированного декодера. Для `report` расширение `x-response-formats` дополнительно связывает `format=docx` с бинарной схемой, а `format=json` — с JSON неизвестной структуры. Это исследовательские метаданные, а не утверждение о Content-Type; стандартный генератор OpenAPI 3.0 сам не выберет декодер по query-параметру. Неизвестно, возможны ли ошибки в теле ответа 2XX. Примеры ответов в снимках пусты. Платные, авторизованные и другие реальные запросы к API не выполнялись; поведение в эксплуатации не проверено.

## report

Таблица запроса определяет `req` как строку ИНН/ОГРН, `format` как `docx` или `json` (по умолчанию `docx`), `sections` как строку разделов и `key`. Значение `sections` по умолчанию и полный перечень разделов с применимостью к ЮЛ и ИП включены в OpenAPI. Значение имени раздела без списка подразделов не уточнено. Генерация может занимать продолжительное время. Описаны файл отчета и JSON-вариант, но структура JSON, точный Content-Type и ошибки отсутствуют. По результатам прежней поисковой выдачи примеры на [странице языков](https://damia.ru/apicalls?id=1) используют `inn` вместо `req`, а Python разбирает JSON без явного `format`, вопреки заявленному умолчанию DOCX; сама страница напрямую не проверена. Поддержка `inn` и фактическое умолчание не проверены.

## proverki

Таблица запроса определяет `req`, семь строковых значений `status`, даты `from_date` и `to_date` в формате YYYY-MM-DD, целочисленный `page` с default 1 и `key`. При пропуске статуса допускаются все статусы; на странице не более 100 проверок. Включительность границ дат, допустимые номера страниц и метаданные пагинации не указаны. Примеры обоих источников используют `regn` вместо табличного `req`: alias не доказан.

Таблицы ответа называют группированный `format=1` и негруппированный `format=2`, но `format` отсутствует среди параметров запроса; механизм выбора, тип и умолчание неизвестны. JSON описан текстом, но точный Content-Type не указан. Полный последовательный каталог полей и типов помещен в `x-research-field-catalog`, а схемы двух вариантов в components — исследовательские гипотезы, не подключенные к валидации ответа. Ответ использует общий media range `*/*`, без утверждения конкретного Content-Type. Снимки уплощают таблицы; согласно прежнему исследованию HTML задает иерархию через `data-id`/`data-parent`: `gAroot` → `g1` → `g2` → `g21`–`g24` (result → Год → Статус → счетчики/РегНомера); `Aroot` → `1` → `10` → `10a` → `10a2`/`10a3` (result → РегНомер → Объекты → Нарушения → СудСведения/Предписания). `108`, `109`, `10b` принадлежат `10` (Инспекторы, Представители, Результаты внутри Объекты), а `1_19` принадлежит `1` (Статус внутри РегНомер). Прежняя интерпретация HTML не проверена повторно и не доказывает вложенность JSON; типы элементов массивов явно не указаны: дочерние строки сохранены в расширениях схем `x-research-child-fields`, не как подтвержденная схема items. По прежнему исследованию имена Год, Статус и РегНомер в HTML отмечены class=quoted; их интерпретация как ключей словарей гипотетична и требует проверки. `РегНомер` указан как object, хотя по описанию это учетный номер. Отсутствуют обязательность, nullable и примеры JSON.

## Приоритеты для SDK и проверок

1. Уточнить у поставщика обязательность и выдачу/совместимость `key`, а также `req` против `regn` и `inn`; до подтверждения не добавлять alias и не записывать секреты в логи.
2. Уточнить выбор формата проверок, реальные JSON-вложенность и типы элементов массивов, тип `РегНомер`, обязательность и nullable; получить обезличенные примеры обоих вариантов.
3. Уточнить статус-коды, ошибки и фактические Content-Type для DOCX и JSON; не строить декодер на предположениях или `default` OpenAPI.
4. Проверить границы дат, номера и завершение страниц, наличие метаданных, семантику разделов без скобок и реальное значение format по умолчанию для отчета.
5. После отдельного разрешения на тестирование проверить документированные сценарии с тестовым ключом и обезличенными данными, лимиты/стоимость и длительную генерацию; предусмотреть управляемый тайм-аут и отсутствие повторного платного запроса без решения клиента.
